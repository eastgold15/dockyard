# 原子依赖图与中间者

本文是 dockyard DI 结构的**顶层设计**，回答四个问题：

1. 原子之间可以怎么依赖
2. 「环」到底在哪一层检测
3. 需要用多个原子的服务时，代码写在哪
4. 这些约束由什么工具强制

---

## 1. 基本单位

```
src/pages/<name>/          = 一个原子 = 一段 URL = 一个可拷贝单元
src/shared/                = 共享层（被多个原子用，无业务语义）
```

原子自带业务完备：`<name>.di.ts`（装配声明）、`<name>.socket.ts`（唯一对外门）、
`<name>.service.ts`、`<name>.repository.ts`、`schema.ts`、`migrations.ts`、
`<name>.actions.ts`（端点）、`client/`（前端）。

**共享层不放进原子的原因**：`src/shared/solid-ui/`、`src/shared/db.ts`、
`src/shared/paths.ts` 被 canvas / servers / projects / deploy 同时使用，
塞进任何一个原子都会变成「别人要反过来依赖这个原子」。共享层是显式存在的，
不是设计缺陷。

---

## 2. 引用路径一律 `@/`

跨原子与共享层引用**必须**写别名，不写相对深度：

```ts
import { DeployService } from "@/pages/deploy/deploy.socket";  // 跨原子
import { db } from "@/shared/db";                              // 共享层
import { CanvasService } from "./canvas.service";              // 同原子：保持相对
```

理由：原子文件夹要能被整体拷走 / 分发。`../../../deploy/deploy.socket`
把本机目录层级焊死在源码里，换一个目录深度就全断。

`tsconfig.json` 的 `paths` 提供映射：

```json
{ "@/*": ["./src/*"] }
```

---

## 3. 跨原子只能走 socket

`<name>.socket.ts` 是原子的唯一对外门。跨原子 import 指向原子内部任何其他文件
都是违规（`elysiax doctor` 与 `codegen` 都会拦）。

```ts
// ✅
import { DeployService } from "@/pages/deploy/deploy.socket";
// ❌ 私拉电线
import { DeployService } from "@/pages/deploy/deploy.service";
```

插座本身还有纯度约束：只许 named / type export，不许 `export default`，
不许导出实例（`export const x = new …`）——共享可变状态必须走 DI。

---

## 4. 环检测在**服务键级**，不在原子级

这是整套设计里最容易搞错的一点。

### 两种粒度

**原子级**：把每个 `*.di.ts` 里所有 provides 的依赖汇总成一条边。

```
canvas  提供 canvasService，依赖 deployService
deploy  提供 deployService，依赖 canvasService
⇒ 原子级判定：canvas ↔ deploy 成环
```

这个判定是**错的**。`canvasService` 不依赖任何 deploy 的键，
只是 canvas 原子里另有一个服务依赖 deploy。

**服务键级**：节点是服务键，边是 `provide(X, [Y])` 里的 Y。

```
boardService    → canvasService, deployService, serverService, …
deployService   → canvasService, …
canvasService   → canvasRepository
canvasRepository → db
```

是一条**链**，不是环。只有真正出现回边（`A → B → A` 的键链路）才算环。

### 所以容器装配顺序也按服务键

`container.gen.ts` 不再按模块成块生成，而是按键的拓扑序逐个 `registerClass`——
每个键的依赖必定先注册（InferDI 的类型链要求）。模块成块会让
「A 模块依赖 B 模块的某个键」被迫整块提前，那正是原子级误判成环的根源。

### 报错长什么样

```
检测到依赖环（按服务键）: deployService（deploy）→ canvasService（canvas）→ deployService（deploy）
```

带键名 + 属主原子，直接指出是哪条边要改。

## 5. 中间者：跨原子组合的唯一落点

actions 的窄类型只含本原子 `*.di.ts` 声明的键。要用别的原子的服务时，
**不在 actions 里直接 `di.get` 别人的服务**，而是在本原子加一个组合服务：

```ts
// canvas.di.ts
export default defineModule({
  route: "/canvas",
  provides: {
    canvasRepository: provide(CanvasRepository, ["db"]),
    canvasService: provide(CanvasService, [CanvasRepository]),
    // 中间者：依赖各原子的服务，自己不被任何服务依赖
    boardService: provide(BoardService, [
      CanvasService, DeployService, ServerService,
      ProjectService, EdgeService, ContainerPoller,
    ]),
  },
});
```

```ts
// canvas.actions.ts —— 只调本原子的键
export default defineRoutes<CanvasServices>()
  .get("/board", async ({ di }) => di.get("boardService").board());
```

`CanvasServices` 由 codegen 自动推导为 `provides ∪ 它们的直接依赖`，
所以 `deployService`、`serverService` 这些依赖键也在类型里，无需借用名单。

### 中间者的硬约束

**必须没有任何服务依赖它** —— 即服务键级图上的叶子。满足这条，
`中间者 → A → …` 和 `中间者 → B → …` 永远成链不成环。

如果加了中间者之后图上出现回边，`gen` 立刻报键链路，不靠人记。

### 位置：住在被组合的那一侧原子内

**不新建假页面目录**。`src/pages/board/` 会让人以为存在 `/board` 页面，
也会占掉一个顶层 URL 段。中间者是实现，不是入口。

| 中间者 | 位置 | 依赖 |
|---|---|---|
| `boardService` | `canvas/board.service.ts` | canvas, deploy, server, project, edge, containerPoller |
| `deployConsoleService` | `deploy/console.service.ts` | deploy, runtime, backup |
| `serverResourceService` | `servers/resource.service.ts` | resource, server |
| `githubPushService` | `github/push.service.ts` | github, updatePoller |

需要独立插座（将来被别的原子引用）时，才升级成嵌套原子
`src/pages/canvas/board/`（各自 `*.di.ts` / `*.socket.ts`，无 page/actions 文件）。
**不建公共 `src/services/` 层。**

## 6. 工具强制

### `elysiax graph`

打印两张图：

```sh
bunx elysiax graph          # 原子级引用图 + 键级汇总
bunx elysiax graph --keys   # 逐键列出依赖
bunx elysiax graph --json   # 机器可读
```

- **原子级引用图**：DI 边（进容器）与 import 边（只引用）分开列。
  给将来的 `elysiax add <atom>` 算依赖闭包用。
- **服务键级 DI 图**：容器排序 + 环检测的唯一口径。

### 其他强制点

| 时机 | 检查 |
|---|---|
| `bun run gen` | 插座门禁（跨原子是否走 socket）、插座纯度、键级环检测、缺失依赖 |
| `bunx elysiax doctor` | 上述全部 + 路由冲突 + client 边界 + 出口只增不减 + 迁移只追加 |
| `bunx tsc --noEmit` | 窄类型：actions 里 `di.get` 了未声明的键直接编译失败 |

## 7. 常见误区

| 误区 | 实际 |
|---|---|
| 「一个文件夹必须完全自包含」 | 不自包含。共享层显式存在，依赖图才是诚实的模型 |
| 「原子级成环 = 必须拆原子」 | 键级不成环就不用拆。中间者就是合法解法 |
| 「中间者要新建顶层目录」 | 住在被组合一侧的原子内，沿用该原子的 URL |
| 「actions 里 `di.get` 别的原子服务，加个 `Pick<ServiceMap>` 就行」 | 借用名单是补丁。要么走中间者，要么说明为什么这个键该在本原子声明 |
| 「lazy 能打破环」 | 不能。`registerClass` 的类型链仍要求依赖先注册 |
