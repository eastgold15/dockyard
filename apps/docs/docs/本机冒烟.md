# 本机部署冒烟手册

改动部署链路（pipeline/forms/归属标签/回滚/运行时对账）之后，用本手册在**本机**把六阶段真实跑一遍：不碰真实数据、不动他人容器，跑完即清。

## 1. 隔离运行环境

dockyard 的数据目录走 XDG，沙盒用一次性目录即可（数据库、仓库缓存、备份、relay 全部落里面）：

```bash
mkdir -p /tmp/dockyard-smoke/{data,cache}
XDG_DATA_HOME=/tmp/dockyard-smoke/data XDG_CACHE_HOME=/tmp/dockyard-smoke/cache \
  bun apps/dockyard/src/index.ts   # 端口硬编码 3003
```

- **用 PID 文件停服务**，不要 `pkill -f 'bun src/index.ts'`——它会匹配到执行 pkill 的 shell 自己
- `ensureDirs()` 必须同步执行：`db.ts` 在模块顶层打开 SQLite，异步建目录会和打开形成竞态（全新 XDG 目录上直接 `unable to open database file`）

## 2. 准备被测项目

一个最小目录即可：`Dockerfile` + `docker-compose.yml`（含 `ports` 与可写探针文件），例如 app 把版本号写进 `/opt/version`，用来验证「重部署后容器真的是新镜像」。

## 3. 走一遍六阶段

1. 画布上右键服务器卡 →「部署本仓库」→ 选**本地文件夹导入**，指向被测目录
2. 观察抽屉与步骤条：源 → 构建 → 传输 → 运行 → 暴露 → 产物
3. 部署完成后核对：
   - `docker inspect <容器> --format '{{json .Config.Labels}}'` 含 `dockyard.managed=true` 与 `dockyard.target-id=<id>`（否则下次 preflight 会把自家容器当别人的）
   - 抽屉 Deployments/Monitor/Console 均可用（容器名推导依赖部署回写的 compose 项目名）
   - 刷新页面后卡片仍显示「运行中」（SSE 首帧含部署状态快照）
4. **重部署**：改版本号再部署一次，确认容器内容真的更新（不是旧容器）
5. **回滚**：在部署历史里回滚到上一产物，确认内容回退
6. （可选）数据库实例：备份 → 改数据 → 恢复，确认恢复前安全备份已生成

## 4. 已知坑（都会伪装成「功能坏了」）

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 同 tag 重建镜像后部署，容器还是旧代码 | `compose config` 哈希只看镜像**名** | `up -d --force-recreate`（`composeUpCommand` 已统一） |
| 重部署被 preflight 拦截「非本工具管理的同名容器」 | 容器创建时没写归属标签，标签创建后不可变 | 删除旧容器重部署；新容器随 up 的 labels 层创建 |
| redis 镜像里新写入的文件被旧内容遮住 | redis 镜像 `VOLUME /data` 的匿名卷在 recreate 时被复用 | 探针写 `/opt`（卷外），或 `docker compose down -v` 后重试 |
| 刷新后已部署卡片显示「未部署」 | SSE 首帧原先只有容器状态 | 首帧已合并部署 status/stage 快照 |
| SSE 500 `Container is disposed (key: "containerPoller")` | 请求作用域释放后异步快照再 `di.get` | 请求内先取出服务再闭包使用 |
| `curl` 看不到 SSE 帧 | 输出缓冲 | 重定向到文件后再读 |

## 5. 清理

```bash
# 容器/网络（在部署目录）
docker compose -p <项目名> down
# 冒烟产生的镜像 tag
docker images | grep 'dockyard-'      # 确认后删除 run-* / 冒烟专用名
# 远端目录与沙盒
rm -rf ~/dockyard /tmp/dockyard-smoke
```

**只删自己创建的**：本机可能有真实业务容器（如 tradeflow），冒烟全程不要动它们。清理完用 `docker ps -a` 复核。
