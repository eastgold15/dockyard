# 部署抽象：六阶段流水线

> 一次部署 = 六条正交轴上的一个坐标：`源 Source → 构建 Build → 产物 Artifact → 传输 Ship → 运行 Run → 暴露 Expose`。

## 为什么是坐标系而不是枚举

枚举式设计（「GitHub 部署」「本地部署」「数据库部署」三个平铺特例）把变化空间锁死在枚举数量上——每加一种部署方式要在所有 if/else 分叉点各插一刀。坐标系式设计把部署描述为六条**正交轴上的坐标**，每条轴上的选项彼此无关：新增部署方式 = 在某条轴上注册一个新坐标，变化空间是各轴基数的笛卡尔积。

## 零界点：Artifact 是原点

六轴全自由是过度自由（多数组合无意义）。流水线在 **Artifact** 处收敛——它是坐标系的原点：

- **前半段（源/构建/传输）三轴自由组合**，但必须汇聚到同一个产物断言：「远端工作目录就绪 + 镜像在目标 docker 守护进程就绪」。
- **后半段（运行/暴露）不看前面任何坐标**，只由产物形态唯一决定。

自由度集中在需要变化的前半段，稳定性锁在后半段。

## 形态映射表（现状四形态）

| 形态 | 源 | 构建 | 产物 | 传输 | 运行 | 暴露 |
|---|---|---|---|---|---|---|
| app/GitHub | git 远端拉 | 远端 docker build | 镜像 | 免（就地） | compose up | 域名+Caddy |
| app/local | 本地目录 | 本地 docker build（跨架构） | 镜像 | save/load + sftp | compose up | 域名+Caddy |
| db 容器 | 模板渲染 | 不构建（官方镜像） | 镜像 | sftp | compose up | 裸端口 |
| db 逻辑库 | 凭据生成 | — | **不穿零点** | — | SQL（旁路） | 连接串 |

逻辑库是**空间外的点**：无产物、无对账、无快照，硬塞坐标系只会让五个轴取假坐标。承认旁路反而保持坐标系纯度。

## Artifact 持久化：deploy_artifacts 表

产物是一等实体，与 run 解耦：

- 部署成功 → `captureArtifact`：镜像打 `dockyard-<targetId>-<svc>:run-<runId>` tag + compose/override/env 快照（enc1 加密）落 `deploy_artifacts`，run 行回写 `artifactId`。
- **回滚 = 激活旧产物**：新 run（trigger=rollback）引用同一 artifact，`activateArtifact` 在独立回滚目录重建快照文件 + pin 旧镜像 tag + `-p` 沿用当初项目名。同一产物可被多次激活。
- tag 失败不阻断部署（产物照存、imageTags 空 = 不可 pin 回滚）。
- `pruneRuns` 连带 GC：产出 run 已清理且无任何存活 run 引用的产物才删。

## 阶段门禁：preflight 归属对账

preflight（容器标签对账，绝不动别人的容器）是**首次远端写入前的门禁**，归 provision 职责，不在共享 activate 里：

- db 容器：任何写入前（模板会覆盖在跑实例目录的 compose/.env）
- app：秘密文件（.env/override）推送前；github 的 clone/build 落检出目录是源阶段本意，不受门禁约束
- 回滚（activateArtifact）自带对账：回滚目录是独立目录，up 前校验容器名归属；`docker compose config` 失败**必须中止**——跳过去会连 preflight 与归属标签一起跳过，容器重建后没有 dockyard 标签，运行时对账再也认不出它

`ServerTransport` 是部署链路的唯一远端能力入口：`exec` + `sftp()`，**没有 `close`**——远程 transport 是 `SshPool` 连接的视图，视图关连接会让池里其他调用方拿到断开的 client（断连走 `ServerService.dropSsh`）。SFTP 由实现方提供（远程在 `remoteTransport` 闭包里持有真 `SshClient`，本机直接落盘），调用方**不得**把远程包装对象强转回 `SshClient` 再 `openSftp`——远端会抛 `TypeError: client.session is not a function`，而本机单测只跑 LocalTransport，永远发现不了这条路径。本机通道用 `bash -c` 而非 `-lc`：登录 profile 的横幅会混进 stdout（`printf $HOME`、`docker version`、base64 备份都是「输出即数据」）；本机落盘固定 0600，与远端 SFTP 的 `chmod 600` 同标准。

**本机判定只认 `servers.builtin`**：`isLocalHost` 只在「添加服务器」门禁里使用（回环地址不许用户添加；归一化大小写、空白、`[::1]`、`127.0.0.2` 等绕过写法）。`pori@127.0.0.1:2222` 是用户自己的 SSH 隧道，走远程通道；启动认领存量本机行也只升级「回环 + 22 端口 + 当前用户」这种与本地进程等价的形态，绝不改写隧道行（改写了会连 host/port/user 一起被覆盖并钉死不可删）。

## 容器归属标签与强制重建

归属标签靠 preflight 拦住别人的容器，那自家容器靠什么证明身份？——**创建时就打上标签**，否则下一次部署 preflight 会把上次自己创建的容器当成「非本工具管理」。

- **标签层压轴**：provision 生成 `docker-compose.dockyard-labels.yml`（`ownershipCompose`，每个服务带 `dockyard.managed=true` + `dockyard.target-id=<id>`），在 `-f` 参数里排在**最后**——compose 多文件合并时后者的 labels 覆盖前者，用户自己的 compose 写了同名 label 也不会赢
- **标签只能在 up 的同一批 `-f` 里创建**：容器创建后标签不可变，事后再补写文件没有任何作用；已在跑的旧容器（无标签）只能删掉重建
- **`up -d` 必须配 `--force-recreate`**：`docker compose config` 的哈希只看镜像**名**不看内容。本地构建重打同名 tag（如 `app:dev`）后，compose 认为配置没变、直接复用旧容器——代码永远是上一版。`composeUpCommand` 统一产出 `up -d --force-recreate`（activate 与 activateArtifact 共用），以容器重建换正确性
- **部署成功后回写 compose 项目名**：`compose config` 的 `name` 缺省等于目录名，与 `docker compose -p` 推导、运行时对账（`dockyard-<id>`）可能不一致。activate 成功即把 `project` 与 `services`（名字/镜像/端口）写回 `target.servicesJson`，运行时 logs/restart/metrics/console 的容器名推导全部依赖它

## 产物位置：门票是 serverId 不是布尔

`artifactShipped` 布尔说不清「产物在哪台服务器」——本地构建的镜像只 load 在当次目标上。落点记录在 `artifactServerId`，移动卡片按目标服务器比对：本地构建的 app 换任何服务器（含 remote→remote 平移）都必须先重传，否则远端 up 会去 pull 一个 registry 里不存在的镜像名。

## 阶段可视化：stage 是进度指示不是状态机

`deploy_runs.stage` 记录流水线当前段（执行序六段：sourcing/building/transferring/deploying/exposing/packaging），经 SSE 并入 status 事件推送，画布部署历史每行内嵌迷你步骤条（`client/pipeline-steps.tsx`）。纪律：

- stage 是 **best-effort 进度指示**，status 才是状态机（六值 CHECK 约束）；stage 列故意无 CHECK，取值域由 TS 层 `DeployStage` 约束
- 终态驻留：failed 时 stage 停在出事段（步骤条红叉的数据源），success 停在 packaging；queued/旁路（逻辑库）/存量行 = null，UI 降级为旧徽章
- 「免」段不走埋点，由 UI 按形态推导：github 免传输、db 容器免构建、回滚只走运行→暴露、ship 止步传输
- **形态判定只认 `sourceTypeOf`**（`deploy.service.ts` 导出的纯函数）：项目显式 `sourceType` 优先，旧数据才按 localPath/repoUrl 推断。部署分派、`/board` 快照、服务抽屉响应共用它——客户端**不能**从「有没有 repoUrl」猜形态：克隆到本地再导入的项目也带 repoUrl，但服务端走 `localAppForm`（本地构建 + 推送，可 ship），按 repoUrl 猜会把它判成 github、把传输段误标成跳过，还会藏掉「传输产物」按钮
- UI 展示按**执行序**（产物落库在容器起来之后），不硬凑本文档概念序里 Artifact 的第三位
- 实时值只合并给「在跑的那一行」（库状态仍为 queued/building/transferring/deploying）：其它行永远用库值，否则当前 run 的状态与段位会串到每一条历史记录上（`mergeLiveRow`，纯函数单测）
- **状态帧带 `runId`**：SSE 的 status/running 事件标明「这是哪一次 run 的状态」，前端合并前比对归属——在跑的可能是上一轮残留的非终态行，当前 run 的状态不能写到它头上；日志抽屉也据此判断实时徽章是否属于正在看的那次 run
- 新 run 的库行 stage 还是 null，步骤条不能按库值判降级——用合并后的 stage；SSE 终态后再拉一次列表对齐库值（含 rollbackable）

## 更新检测：版本来源必须与部署形态同源

`update-poller` 每 60s 给每个 app 目标取「最新源码版本」，与 `lastKnownSha` 比对后按 `deployPolicy` 行事（manual 不轮询 / notify 亮徽章 / auto 直接部署）。

- 本地来源（`sourceType=local`）看**本地 git HEAD**（`localAppForm` 用的就是这个 sha）；GitHub 来源看分支最新 sha——来源必须和部署形态同源，否则「本地构建的卡片永远不亮徽章」或「GitHub 的改动触发了本地构建」
- 本地来源只认已提交的 HEAD：工作区未提交改动不算更新（未提交的代码不该被自动部署）
- auto 防风暴：内存记「上次 auto 触发的 sha」，同一 sha 部署失败不每分钟重试；新 sha 才再次触发

## 备份与恢复：先留退路再覆盖

备份链路：容器内 dump → gzip → base64 → 控制面本地落盘（`~/.local/share/dockyard/backups/target-<id>/`）。ssh exec 是文本通道，二进制必须 base64 过。

恢复是**破坏性操作**，纪律：

- **先安全备份**：恢复前自动做一次当前数据的 dump，失败即中止——绝无退路地覆盖
- **备份不许假成功**：dump → gzip → base64 不能写成一条管道（退出码只取最后一段，dump 失败也会产出空备份）。命令逐段判错 + 非空校验 + `gzip -t` 自检，空结果直接拒绝入列表
- **dump 要可重放，且是 best-effort**：postgres 用 `pg_dumpall --clean --if-exists`，恢复时先 DROP 再 CREATE。`--clean` 的 dump 以当前连接用户身份重放时，`DROP ROLE <自己>` 必然报「当前用户不能删除」、随后 `CREATE ROLE` 撞「已存在」——所以用 `ON_ERROR_STOP=0` 让它按幂等方式继续（语句级错误不中断，数据仍被 DROP/CREATE 重放），**连接/认证失败才由退出码判失败**。这两条必然噪声不计入告警，其余非预期语句级错误照实作为 warnings 上报，不把「有一堆 ERROR」说成干净恢复
- **恢复前先验备份**：`[ -s ]` + `gzip -t` 双检，损坏/半截的 gz 在灌库之前就被拦下（管道里 gunzip 的失败会被最后一段掩盖，不能靠 pipefail）
- **恢复与部署互斥**：同一 target 正在恢复或正在部署/回滚时拒绝（容器被重建时灌数据会把实例写坏）。互斥占位必须在检查**之后立刻同步**完成——中间隔着查库/建通道的 await，双击或双标签页会在窗口里双双通过；`backupNow` 同样要拦部署中的目标，否则重建中途 dump 出的偏斜快照会被当成可用备份留下
- **灌数据走宿主管道**：备份 SFTP 传到宿主临时目录（0600，dump 含口令哈希），`gunzip -c | docker exec -i <容器> sh -c '…'`；凭据必须在容器内展开（`docker exec` 不展开宿主变量），无论成败都删除宿主临时文件
- **容器名来自用户输入**：拼进宿主 shell 前一律单引号转义（`shq`），资源名在建时就用白名单校验
- **能力按引擎显式登记**（`RESTORE_SUPPORT`）：postgres/mongo 可自动恢复；mysql 的 `--all-databases` 含 mysql 系统库（恢复时重建 grants 风险大）、redis 的 RDB 必须停容器换文件 → 两者只提供下载，提示手动执行。client 不重复维护引擎清单，由抽屉数据里的 `backupRestorable` 下发
- **二次确认**：UI 先进入确认条，API 的 `confirm` 是字面量 `true`（类型层面挡掉误调用）

## 已知耦合缝（记账）

- **upServices 在 target 侧而非产物侧**：activateArtifact 用「当前」upServices 过滤「历史」imageTags。当前 upServices 无修改入口（仅创建时写入），两者恒一致；一旦将来开放修改，产物模型出现时间错位——届时 upServices 要沉进 artifact。
- **run 旧快照三列**（imageSnapshot/snapshotJson/project）：0017 回填后停写留读，属死列；确认所有存量库过完 0017 后可连同 artifactOfRun 的合成兜底一起删。
- ~~**db 模板 project 疣**~~（已修）：`dbCompose` 现在渲染顶层 `name: dockyard-<targetId>`（共享资源 `dockyard-res-<id>`），项目名不再随目录漂移；项目名随模板落库（`rendered.project`），存量模板无此字段则沿用旧行为（目录名），升级不换项目名。

## 能力登记（预留）

`serverCaps(serverId)`（arch + buildx 探测，内存缓存）是「服务器能力清单」的雏形：同一组坐标在能力不同的服务器上可不可达，应由值域判定而非流程写死。本轮只做接口收敛，不建表。
